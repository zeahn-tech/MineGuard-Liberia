# 25 — Public User programme: implementation report and release runbook

Status of the work, what changed, how to release it safely, and how to undo it. Written at the end of
Phase E. Nothing in this document has been applied to a production database or deployed by the people who
built it: **applying migrations and deploying remain explicit owner decisions.**

Legend — **Done**: built and in the repository. **Tested**: covered by an automated test that ran green.
**Pending**: needs an owner action. **Unverified**: could not be checked from the build environment.

## 1. What the programme delivers

MineGuard Liberia now welcomes ordinary members of the public without opening anything private.

| Capability | Status |
|---|---|
| Anyone can register; a new account has **no role** (`profiles.role IS NULL`) — it never receives company or Ministry privileges | Done · Tested |
| A public user is decided by the database, not the browser: authenticated, not an anonymous guest, has an e-mail, no role, no active company membership, not restricted (`mg_is_public_user`, `mg_is_verified_public_user`, `mg_my_access_class`) | Done · Tested |
| Anonymous guests stay read-only and are kept apart from registered users at the database level | Done · Tested |
| Nobody can become administrator by registering (three separate paths closed) | Done · Tested |
| Anonymous reporting unchanged; a verified user may **opt in** to link a report to their account and follow it under *My reports* | Done · Tested |
| Feedback and questions from verified accounts, answered in-app by Ministry reviewers | Done · Tested |
| Ministry can restrict an abusive **public** account (administrator RPC; no screen yet) | Done · Tested (RPC) |
| Approved public content with a four-eyes lifecycle: glossary terms, safety guidance, notices, statistics | Done · Tested |
| Public information area (`/public/*`) and registered-user dashboard (`/account/*`) | Done · typecheck/build only (see §6) |
| The existing 229-term glossary prepared as **unpublished drafts** (English only) | Done · Tested |
| Live, all-company anonymous statistics retired | Done · Tested |
| Public → company worker through the existing governed process, one account throughout, audited | Done · Tested |

## 2. Files, database objects and security changes

**Migrations (in order):** `0047_close_admin_bootstrap`, `0048_public_user_identity`,
`0049_public_reports_feedback`, `0051_public_content`. (`0050` is the separate Ministry Voice work already on
`main`; the public-content migration took `0051` to avoid the collision. A test now blocks new duplicate numbers.)

**New tables:** `account_restriction_events`, `public_feedback`, `public_content`, `public_content_events`.
**New columns:** `profiles.restricted_at`, `community_reports.submitter_id`. **New enum value:**
`report_category.other` (cannot be removed; harmless if unused). **New permissions:** `content.author`,
`content.review`, `content.publish`.

**New functions (all re-check who is calling):** `mg_is_anonymous`, `mg_is_public_user`,
`mg_is_verified_public_user`, `mg_my_access_class`, `mg_set_account_restriction`,
`submit_my_community_report`, `mg_my_community_reports`, `submit_public_feedback`, `mg_my_feedback`,
`mg_feedback_queue`, `mg_respond_feedback`, `mg_content_can_view`, `mg_content_save`,
`mg_content_transition`, `mg_content_revise`, `mg_content_list`, `mg_content_get`.

**Functions replaced (bodies preserved, one rule added or removed):** `mg_guard_profile_update`
(first-run admin branch **deleted**; `restricted_at` admin-only), new `mg_guard_profile_insert`,
`complete_staff_profile` (role holders only; never touches role, scope, county, company),
`mg_search_companies` (verified, non-anonymous, 20 searches/minute), `mg_guard_report_update` (ownership and
tracking code immutable), `mg_register_push_subscription` and `mg_update_my_profile` (no guests),
`mg_prepare_account_deletion_core` (report and message owner links cleared first).
`mg_any_profile_role` is no longer executable by any client.

**Policies and grants changed:**
- `profiles`: new insert guard trigger; update guard extended.
- `community_reports`: no new policy — owners read through a curated function, never the table.
- `public_content`: one policy (published, in-date rows) + **column grants** for the public columns only; no write grants.
- `public_feedback`, `account_restriction_events`: reviewer / administrator read policy; no write grants.
- `public_content_events`: no client access.
- `meta`: the anonymous read policy and grant were **removed**; staff read only.

**Operational files:** `supabase/maintenance/rollback_0047…0049…0051*.sql`, `supabase/checks/admin_present.sql`,
`supabase/checks/migration_state.sql` (markers for each migration), `supabase/seeds/public_glossary_drafts.sql`
(generated by `scripts/gen-public-glossary-seed.mjs`; `--check` fails if stale).

**Interface:** public pages `/public`, `/public/glossary`, `/public/safety`, `/public/notices`; account pages
`/account`, `/account/reports`, `/account/feedback`, `/account/profile`, `/account/security`; staff screens
*Public Feedback* and *Public Content*; the report form's opt-in link checkbox; the staff self-onboarding
choice ("I am Ministry staff") **removed**.

## 3. Tests

Real Postgres (PGlite) with every production migration applied — not mocks. New suites:
`phase-a-security`, `phase-b-public-identity`, `phase-c-public-reports`, `phase-d-public-content`,
`public-surface-matrix`, `migration-hygiene`. Each security suite was also run against a deliberately
weakened copy of its migration to prove it fails when the protection is removed.

`public-surface-matrix` is the broad net: it calls **every function a signed-in session can execute**
(214 today) with benign arguments as an anonymous caller, a guest, an unverified, a verified and a
restricted account, and fails if any of them can change state or read rows outside a short reviewed
allowlist (`refresh_public_stats`, `mg_prepare_account_deletion`, `mg_set_my_avatar`). It also pins what every
persona can read from every table, bans unconditional policies, pins anon's column-level reads, and walks the
whole public → company member → public journey. A new function or table that exposes anything to the public
fails these tests until someone reviews it.

Final run on the Phase E branch (all four programme migrations plus everything else on `main`): **1629 passed, 4 skipped, 0 failed**; typecheck and build clean; lint 0 errors (2 warnings that predate the programme). The 4 skipped tests need a live database and are skipped in every run.
CI runs the full suite, and the required `rls-security-test` job now names every Public User suite.

## 4. Required Supabase configuration (check before release) — **Unverified**

The build environment cannot reach the live Supabase project. Check each of these in the dashboard:

1. **Authentication → Providers → Email → "Confirm email" = ON.** Account-based features need verified e-mail.
2. **Authentication → Sign In / Providers → "Allow anonymous sign-ins"** = ON only if you want guest browsing.
3. **Bot protection (CAPTCHA)** on sign-ups and anonymous sign-ins; **rate limits** for sign-ups, sign-ins and
   e-mail. Anonymous sign-ins are free account creation — protect them.
4. **Custom SMTP.** The built-in sender has a very low hourly cap; public registration needs a real provider.
5. **Password strength** (length, and leaked-password protection if your plan offers it) and **Site URL /
   redirect URLs** for password reset (the GitHub Pages address).
6. **Storage:** buckets `evidence` and `avatars` must be **private**.
7. After deploying, sign in as a guest and run `select public.mg_my_access_class();` — it must return
   `anonymous_guest`. This confirms the database sees Supabase's `is_anonymous` token claim.

## 5. Release runbook

**Before anything**
1. Confirm a recent backup (the existing backup workflow). Take a manual one if unsure.
2. Run `supabase/checks/admin_present.sql`. If it reports `NO ADMINISTRATOR`, run
   `supabase/maintenance/promote_to_admin.sql` first — after 0047 nobody can claim admin from the app.
3. Run `supabase/checks/migration_state.sql` to see what the live database already has (the live schema may
   differ from the repository's history).

**Apply, in order, one at a time, checking the app between steps:** `0047` → `0048` → `0049` → `0050`
(Ministry Voice) → `0051`. Each file is a single transaction and idempotent. Then re-run `migration_state.sql`.

**Optional:** run `supabase/seeds/public_glossary_drafts.sql` once as the project owner to load the glossary
as drafts. Nothing becomes public until reviewers approve and an administrator publishes each term.

**Deploy the frontend** only after the migrations. (A frontend that arrives before 0048/0049/0051 degrades
safely: the access-class lookup returns "unknown" and the new pages show their empty states.)

**Smoke test (about 15 minutes)**
- Signed out: `/public` and the glossary load; `meta` cannot be read; no private page is reachable.
- Guest: can read public pages and send an anonymous report; cannot open `/account`.
- Register a new account, confirm the e-mail, land on `/account`; send a report with the link box ticked and see
  it under *My reports*; send feedback.
- As a reviewer: answer the feedback; author, review (as a second person), approve and publish one notice; see it
  on `/public/notices`; archive it.
- Company and Ministry users: sign in and confirm their normal screens and data are unchanged.

**Rollback** — reverse order, only the layers you need, each in its own transaction:
`rollback_0052_public_content.sql` (loses content and history; re-opens anonymous live statistics),
`rollback_0050_public_reports_feedback.sql` (loses feedback and report owner links),
`rollback_0049_public_user_identity.sql` (loses restriction records),
`rollback_0047_reopens_admin_bootstrap.sql` (**re-opens the self-service administrator bootstrap — avoid**).
The frontend can be rolled back independently by redeploying the previous build.

**Watch after release** (queries for the SQL editor)
- Public accounts: `select count(*) from profiles where role is null and deleted_at is null;`
- Restricted: `select count(*) from profiles where restricted_at is not null;`
- Pending work: `select status, count(*) from public_feedback group by 1;` and
  `select status, count(*) from public_content group by 1;`
- Abuse signals: `select bucket, count from rate_limits order by count desc limit 20;`

## 6. Remaining limitations and risks

- **Not run here:** browser end-to-end and accessibility scans (Playwright browsers are not installable in the
  build environment). The public pages are added to the accessibility route list in `e2e/a11y.e2e.ts`; run it
  before release. **Unverified.**
- **Live Supabase behaviour:** tests use a real Postgres with stand-ins for Supabase's `auth` and `storage`
  schemas. The `is_anonymous` claim, e-mail confirmation and storage behaviour must be confirmed in staging (§4).
- `refresh_public_stats` is still executable by anonymous callers and rewrites a row nobody can read any more.
  Harmless, but it is an unauthenticated write endpoint with no purpose; revoking it is a small follow-up
  (it is pinned in the allowlist tests).
- The report tracking lookup falls back to one shared rate-limit bucket when no client IP is available, so a
  determined attacker could exhaust it for everyone (low severity; pre-existing).
- The audit trail keeps a deleted account's old identifier inside its history text; the profile itself is scrubbed.
- No screen yet for restricting a public account (administrators call `mg_set_account_restriction`).
- Review workload: 229 glossary terms must each be reviewed; first-aid, PPE and similar safety content is
  deliberately **not** imported (it needs qualified review) and is written in the editor.
- Evidence uploads by public users are **not** implemented. When built they need their own restricted bucket,
  validation and review — never a loosening of the existing evidence policy.
- A company and site directory is deferred until the Ministry defines approved public fields.
- English only. No French content or French interface exists; none is claimed.
